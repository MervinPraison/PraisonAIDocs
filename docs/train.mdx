<Info>
Two training flows: **`llm`** fine-tunes a base model on your dataset (needs the heavy ML stack), and **`agents`** improves an agent through iterative feedback loops (lightweight, no CUDA/Unsloth).
</Info>

## Standalone Install

Training now ships as its own package (`praisonai-train`, import `praisonai_train`). Install just what you need:

```bash
pip install praisonai-train              # agent training (LLM-as-Judge + human feedback), no CUDA/Unsloth
pip install "praisonai-train[llm]"       # + Unsloth / torch fine-tuning stack
```

The standalone CLI exposes the training commands directly:

```bash
praisonai-train agents --input "What is Python?" --iterations 3
praisonai-train llm dataset.json --model llama-3.1
praisonai-train list
praisonai-train show <session>
praisonai-train apply <session>
```

<Note>
The wrapper CLI `praisonai train ...` still works — it now bridges into `praisonai-train` when the standalone package is installed (and is hidden on code-only installs). `pip install "praisonai[train]"` (previously an empty extra) now pulls `praisonai-train[llm]`.
</Note>

## Quick Start

<Steps>
<Step title="LLM Fine-tuning">

Fine-tune a base model on your dataset with Unsloth. Pick the tab for your model family — the trainer uses each model's own chat template, so `chat_template` is optional.

```bash
pip install "praisonai-train[llm]"
```

<Tabs>
<Tab title="Llama">

```bash
praisonai-train llm dataset.json \
    --model unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit
```

Optional YAML override: `chat_template: "llama-3.1"`.

</Tab>
<Tab title="Gemma">

```bash
praisonai-train llm dataset.json \
    --model unsloth/gemma-2-2b-it-bnb-4bit
```

Optional YAML override: `chat_template: "gemma"` (or `"gemma-2"`).

</Tab>
<Tab title="Qwen">

```bash
praisonai-train llm dataset.json \
    --model unsloth/Qwen2.5-0.5B-Instruct-bnb-4bit
```

Optional YAML override: `chat_template: "qwen-2.5"`.

</Tab>
</Tabs>

</Step>

<Step title="Agent Training">

Improve an agent iteratively with LLM-as-Judge or human feedback.

```python
from praisonaiagents import Agent

agent = Agent(instructions="You are a helpful assistant.")
```

```bash
pip install praisonai-train

praisonai-train agents --input "What is Python?"
```

One `pip install praisonai-train` gives you the agent, the trainer, and the grader — `litellm` ships as a core dependency, so live LLM-as-Judge grading works with no extra install.

Runs cleanly on Windows and other non-UTF-8 consoles — the summary automatically falls back to ASCII (`PASSED` / `NEEDS WORK`) with no configuration needed. Exit codes: `0` = training persisted, `1` = training failed, `130` = interrupted. See [Train CLI → Exit Codes](/docs/cli/train#exit-codes).

<Note>
`--iterations` sets the **maximum** number of training loops. In LLM-as-Judge mode, training **stops early** when any iteration scores **≥ 9.5** (excellent), so easy prompts may finish in a single iteration. Pass `--no-early-stop` to force all iterations, or `--verbose` to see when it stops. See [Train CLI → Early Stop](/docs/cli/train#early-stop-llm-mode) for the full flow.
</Note>

</Step>
</Steps>

## Beginner-safe defaults

A minimal config trains locally and never pushes to a hub unless you ask it to.

A config with just `model_name`, `max_seq_length`, and `dataset:` trains locally and saves the LoRA to `lora_model/`. Publishing to Hugging Face or Ollama is opt-in — set the flag **and** the target name. Response-only masking auto-probes the tokenizer, so `assistant_only_loss: auto` is safe on any template.

```mermaid
graph TB
    Q1{What do I want?}
    Q1 -->|Just train locally| Local[No publish flags<br/>saves to lora_model/]
    Q1 -->|Publish to Hugging Face| HF[huggingface_save: true<br/>+ hf_model_name]
    Q1 -->|Publish to Ollama| Ol[ollama_save: true<br/>+ ollama_model]

    classDef question fill:#F59E0B,stroke:#7C90A0,color:#fff
    classDef success fill:#10B981,stroke:#7C90A0,color:#fff
    classDef config fill:#6366F1,stroke:#7C90A0,color:#fff

    class Q1 question
    class Local success
    class HF,Ol config
```

Three safety guarantees:

- **Minimal config trains locally** — no push, no missing-repo crash.
- **`assistant_only_loss: auto` never crashes** on a stock Gemma / Qwen / Llama template — it falls back to full-sequence SFT.
- **Unknown / misnamed keys warn instead of crashing** — typos are [collected into one block with `did you mean` suggestions](#config-validation) and training continues.

<Info>
Expected failures now print a single `ERROR: <message>` line to stderr — no Python traceback. `Ctrl-C` prints `Interrupted.` See [Train CLI → Exit codes](/docs/cli/train#exit-codes) for the full table.
</Info>

Three runtime NOTEs surface behaviour that used to be silent — read them if the console shows something unexpected:

- **`num_samples` slices the head, before shuffle.** Setting `dataset[].num_samples: N` without `shuffle: true` trains on the **first N rows** — often sorted by topic and unrepresentative. The trainer prints `NOTE: num_samples takes the FIRST N rows before shuffle; add shuffle: true to sample randomly.` Add `shuffle: true` to the dataset entry to sample uniformly.
- **`split_type: validation`/`test`/`eval` is added to training, not held out.** These splits are **concatenated into the training set**. The trainer warns: `WARNING: dataset split_type 'validation' is ADDED to the TRAINING data (not held out). Use val_split_ratio for a held-out eval set.` Use `val_split_ratio: 0.05` for a real held-out set.
- **`max_steps: 2800` fires when neither length is set.** With neither `num_train_epochs` nor `max_steps`, the trainer defaults to `max_steps: 2800` and prints `NOTE: neither num_train_epochs nor max_steps set; defaulting to max_steps: 2800. Set num_train_epochs: 1-3 (or max_steps) to control training length.`

## Preflight validation

Before any model download or GPU load, the trainer fails fast with one friendly line for the four most common non-developer misconfigurations.

```mermaid
graph TB
    Start[praisonai-train llm config.yaml] --> P{Preflight}
    P -->|No CUDA GPU| GPU[❌ No CUDA GPU detected]
    P -->|Publishing on, no HF token| HF[❌ No Hugging Face credentials]
    P -->|< 10 GB free on training disk| Disk[❌ Low disk]
    P -->|quantization_method typo| Q[❌ quantization_method 'q4km' is not valid]
    P -->|All checks pass| Go[✅ Model load starts]

    classDef entry fill:#6366F1,stroke:#7C90A0,color:#fff
    classDef check fill:#F59E0B,stroke:#7C90A0,color:#fff
    classDef fail fill:#8B0000,stroke:#7C90A0,color:#fff
    classDef pass fill:#10B981,stroke:#7C90A0,color:#fff

    class Start entry
    class P check
    class GPU,HF,Disk,Q fail
    class Go pass
```

| Preflight check | Message when it fails | Fix |
|---|---|---|
| CUDA GPU (skipped when `train: false`) | `No CUDA GPU detected. Fine-tuning needs a GPU. On a rented box check the driver; on CPU it cannot run.` | Use a GPU box; on a rented VM re-install CUDA drivers. Set `train: false` to publish/export on CPU without training. |
| Hugging Face credentials (only when `huggingface_save` / `huggingface_save_gguf` / `push_to_hub` is on) | `Publishing to Hugging Face is enabled but no credentials were found. Run 'huggingface-cli login' or 'export HF_TOKEN=hf_...'. To train without publishing, set huggingface_save: false.` | Run `huggingface-cli login` (cached tokens count) **or** `export HF_TOKEN=hf_...`. |
| Low disk (`< 10 GB` free on `output_dir` or `.`) | `Low disk: only 3.2 GB free on the training disk (need ~10 GB minimum). Free up space or set output_dir to a larger disk.` | Free space, or set `output_dir` in `config.yaml` to a larger volume. |
| Quantization method (only when `huggingface_save_gguf` or `ollama_save` is on) | `quantization_method 'q4km' is not valid. Choose one of: bf16, f16, q2_k, q3_k_m, q4_0, q4_1, q4_k_m, q5_0, q5_1, q5_k_m, q6_k, q8_0.` | Use one of the values below. |

The **12 valid `quantization_method` values**: `q4_k_m`, `q5_k_m`, `q8_0`, `q4_0`, `q4_1`, `q5_0`, `q5_1`, `q3_k_m`, `q6_k`, `f16`, `bf16`, `q2_k`.

<Note>
The GPU check is skipped when `train: false`, so `praisonai-train export` and publish-only runs work on a CPU laptop. Hugging Face credentials are accepted from **either** an env var (`HF_TOKEN` / `HUGGING_FACE_HUB_TOKEN`) **or** a cached `huggingface-cli login` — an env var is not mandatory.
</Note>

## How It Works

Point the trainer at a base model and dataset to fine-tune, or at a scenario to iteratively improve an agent.

```mermaid
sequenceDiagram
    participant User
    participant Trainer
    participant Grader as Grader / HF / Ollama

    User->>Trainer: praisonai-train llm dataset.json
    Trainer->>Trainer: Fine-tune with LoRA (Unsloth)
    Trainer->>Grader: Push model with HF_TOKEN
    Grader-->>User: Published model

    User->>Trainer: praisonai-train agents --input "..."
    Trainer->>Grader: Grade agent output (LLM or human)
    Grader-->>Trainer: Score + suggestions
    Trainer->>Trainer: Re-run with feedback (up to N iterations)
    Trainer-->>User: Improved agent + session ID
```

**Real interaction — agent-training path:** an agent gives so-so answers → run `praisonai-train agents --input "Explain AI" --human` → review N iterations → `praisonai-train apply <session_id> --run "Explain AI"` bakes the improvements into the agent via hooks → the same agent answers better.

## CLI Reference

The `praisonai-train` CLI groups subcommands into **data** (`generate`, `validate`, `benchmark`, `dedup`), **training** (`llm`, `agents`), **serving / export** (`serve`, `export`), and **utilities** (`list`, `show`, `apply`).

| Subcommand | What it does | Deep link |
|------------|--------------|-----------|
| `generate` | Produce synthetic instruction/response rows from a recipe | [Dataset Tooling](/docs/features/praisonai-train-dataset-tooling) |
| `validate` | Score / QC an existing JSONL against the recipe's checks | [Dataset Tooling → validate](/docs/features/praisonai-train-dataset-tooling#validate) |
| `benchmark` | Compare deployments by throughput, latency, and success rate | [Speed Benchmark](/docs/features/praisonai-train-benchmark) |
| `dedup` | Exact + MinHash/LSH near-dedup across many JSONL files | [Cross-file dedup](/docs/features/praisonai-train-dataset-tooling#cross-file-dedup) |

| `list` | List locally available recipes / adapters | [Train CLI → list](/docs/cli/train#praisonai-train-list) |

## Serve a trained model

Run a trained GGUF on an OpenAI-compatible endpoint — MTP fast inference auto-enables for Gemma-4.

```bash
# Serve a trained Gemma-4 model on http://localhost:8080/v1 (MTP auto-enabled)
praisonai-train serve --gguf model.gguf

# Or point at a trained model directory (GGUF auto-detected)
praisonai-train serve -d lora_model

# One-shot speed test with drafter acceptance rate
praisonai-train serve --gguf model.gguf --benchmark

# Custom port, no MTP
praisonai-train serve --gguf model.gguf --no-mtp-draft --port 9000
```

Every flag, with its default:

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--gguf` | `str` | *unset* | Path to the target GGUF to serve. |
| `--model-dir` / `-d` | `str` | *unset* | Directory of the trained model (GGUF auto-detected, drafter files skipped). |
| `--config` / `-c` | `str` | *unset* | Optional `config.yaml` for base-model / MTP knobs. |
| `--base-model` | `str` | *unset* | Base model id used to select the MTP drafter. |
| `--mtp-draft` / `--no-mtp-draft` | `bool` | `True` | Use the stock MTP drafter — on automatically when the family supports it. |
| `--spec-draft-n-max` | `int` | `2` | Max tokens the MTP drafter proposes per step. |
| `--port` | `int` | `8080` | Port for `llama-server`. |
| `--ngl` | `int` | `99` | Number of layers to offload to the GPU. |
| `--benchmark` | `bool` | `False` | Run a one-shot speed benchmark instead of serving. |

A non Gemma-4 model serves without MTP and says so — no configuration needed. The base model name (which drives drafter selection) is recovered in this order: `--base-model` > `--config` `model_name` > the model dir's `config.json` `_name_or_path`.

<Note>
`serve` needs a **llama.cpp** binary (`llama-server` / `llama-cli`) on your `PATH`. Build it from [llama.cpp](https://github.com/ggml-org/llama.cpp) (`cmake -B build && cmake --build build`) or download a release, then add it to `PATH` or set `LLAMA_CPP_BIN` to the binary or its directory. See [Serve trained models](/docs/features/train-serve) for the full walkthrough and MTP details.
</Note>

## Export an already-trained model

Publish or convert a locally-trained model without re-running training.

```bash
# Publish a locally-trained model to Ollama with a q4_k_m quantization
praisonai-train export ollama --model-dir lora_model --ollama yourname/mymodel --quant q4_k_m

# Publish merged weights to Hugging Face
praisonai-train export hf --model-dir lora_model --hf yourname/mymodel-hf

# Produce a LOCAL .gguf (ready to serve) and also push it to the Hub
praisonai-train export gguf --model-dir lora_model --quant q4_k_m --hf yourname/mymodel-gguf
```

The first argument is the target — `ollama`, `gguf`, or `hf`. Every flag:

| Flag | Type | Default | Description |
|------|------|---------|-------------|
| `--model-dir` / `-d` | `str` | *required* | Directory of the already-trained model. |
| `--config` / `-c` | `str` | *unset* | Optional `config.yaml` for extra export knobs. |
| `--ollama` | `str` | *unset* | Ollama model name, e.g. `yourname/mymodel`. Required for the `ollama` target. |
| `--hf` | `str` | *unset* | Hugging Face repo id, e.g. `yourname/mymodel`. Required for the `hf` target. |
| `--quant` | `str` | *unset* | Quantization method for `gguf` / `ollama`, e.g. `q4_k_m`. |
| `--base-model` | `str` | *unset* | Base model id (for chat-template selection). |
| `--mtp-draft` / `--no-mtp-draft` | `bool` | `False` | Also download the stock MTP drafter (Gemma-4 only) for fast inference. |

The `gguf` target always writes a **local** `.gguf` (so you can `serve` it) and only additionally pushes to the Hub when `--hf` is set. The model name (which drives chat-template selection) falls back to the trained model's `config.json` `_name_or_path`, then the directory name, when `--base-model` / `model_name` aren't given.

<Tip>
Export to a local GGUF, then serve it in one hop:

```bash
praisonai-train export gguf --model-dir lora_model --quant q4_k_m
praisonai-train serve -d lora_model
```
</Tip>

## Clean errors & preflight

Fine-tuning validates the environment up front and fails with a single actionable line — no traceback — so a non-developer knows exactly what to fix.

```mermaid

    Tok -->|OK| Disk{≥ 10 GB free?}
    Disk -->|No| E3[ERROR: Low disk]

    Quant -->|No| E4[ERROR: invalid quantization_method]
    Quant -->|Yes| Run[✅ Training runs]

    classDef input fill:#8B0000,stroke:#7C90A0,color:#fff
    classDef question fill:#F59E0B,stroke:#7C90A0,color:#fff
    classDef error fill:#6366F1,stroke:#7C90A0,color:#fff
```

What to expect:

</Note>

## Fine-tuning Setup

Push a fine-tuned model to Hugging Face and Ollama.

### Hugging Face token

```bash
export HF_TOKEN="${HF_TOKEN:?Set HF_TOKEN in your shell}"
```

### Chat Template

Leave `chat_template` unset for tokenizers that ship their own — the trainer uses the model's native template and only overrides it when you set the key.

```mermaid
graph TB
    Q1{Model?}
    Q1 -->|Gemma 2 / Gemma 3| G[Leave chat_template unset<br/>native Gemma template]
    Q1 -->|Qwen 2.5 / Qwen3| Qw[Leave unset OR<br/>chat_template: qwen-2.5]
    Q1 -->|Llama 3.x| L[Leave unset OR<br/>chat_template: llama-3.1]
    Q1 -->|No built-in template| E[Must set chat_template<br/>or trainer raises ValueError]

    classDef question fill:#6366F1,stroke:#7C90A0,color:#fff
    classDef process fill:#189AB4,stroke:#7C90A0,color:#fff
    classDef success fill:#10B981,stroke:#7C90A0,color:#fff
    classDef warning fill:#F59E0B,stroke:#7C90A0,color:#fff

    class Q1 question
    class G,Qw,L success
    class E warning
```

If a model has no built-in template and you leave `chat_template` unset, the trainer fails fast with a clear error you can grep for:

```text
Tokenizer for model '<name>' has no chat template and none was provided via config 'chat_template'. Set 'chat_template' (e.g. 'gemma', 'qwen-2.5', 'llama-3.1') so conversations format correctly.
```

### Multi-Model Fine-tuning

Gemma and Qwen now fine-tune out of the box with their native templates — no config needed.

```bash
praisonai-train llm dataset.json --model unsloth/gemma-2-2b-it-bnb-4bit
praisonai-train llm dataset.json --model unsloth/Qwen2.5-0.5B-Instruct-bnb-4bit
```

Both commands are the two models the SDK actually tests (2× RTX A6000). Forcing `llama-3.1` on every model was the old default and silently corrupted Gemma/Qwen training.

### Assistant-only Loss

Response-only loss is on by default via `assistant_only_loss: auto` — the trainer probes the tokenizer and enables masking only when the template supports it.

```yaml
assistant_only_loss: auto   # default — probe the template, mask if supported
```

The trainer calls the tokenizer's chat template with `return_assistant_tokens_mask=True`; if the template exposes `{% generation %}` markers, masking is enabled, otherwise the trainer trains on the full sequence with no error.

| Value | Behaviour | When to use |
|-------|-----------|-------------|
| `auto` | Probe the template; mask if supported, else full-sequence SFT | **Recommended default** — safe on any template |
| `true` | Force masking; fails fast at model-prep time if unsupported | You know your template emits `{% generation %}` markers |
| `false` | Force off — train on the full sequence | You want full-sequence loss regardless |

`train_on_responses_only` is accepted as an alias for `assistant_only_loss` if you're migrating from an older config. Both real YAML booleans (`assistant_only_loss: true`) and the string forms (`"true"` / `"false"` / `"yes"` / `"no"` / `"on"` / `"off"`) work.

<Warning>
`assistant_only_loss: true` on a template without `{% generation %}` markers raises `ValueError` at model-prep time:

```
ValueError: assistant_only_loss is enabled but the chat template for
'<model_name>' has no assistant-turn markers ({% generation %}). Set
assistant_only_loss: auto (recommended) or false, or use a chat_template
that supports masking.
```

Use `auto` (recommended) or `false`, or set a `chat_template` that supports masking.
</Warning>

## Requirements

<Note>
Training dependencies are checked at startup via `unsloth` package availability but only fully loaded when training commands run.
</Note>

**Install training dependencies:**
```bash
pip install "praisonai-train[llm]"       # LLM fine-tuning (Unsloth / torch / CUDA)
pip install praisonai-train              # agent training (LLM-as-Judge + human feedback) — no CUDA/Unsloth
pip install "praisonai[train]"           # via the wrapper — pulls praisonai-train[llm]
```

Pick the flavour that matches your flow: **agent training** (`praisonai-train`) needs no CUDA/Unsloth — its base install already pulls `litellm` for live LLM-as-Judge grading — while **LLM fine-tuning** (`praisonai-train[llm]`) pulls the full torch/Unsloth stack.

`pip install "praisonai-train[llm]"` installs the whole ML stack for you — you only run the base install:

| Package | Minimum floor |
|---------|---------------|
| `transformers` | `>= 4.51.3` |
| `unsloth` | `>= 2025.9.1` |
| `trl` | `>= 0.18.2` |
| `peft` | `>= 0.13.0` |
| `accelerate` | `>= 0.34.0` |
| `bitsandbytes` | `>= 0.45.0` |
| `torch` | `>= 2.6.0` (CUDA 12.4) |

Verified end-to-end on unsloth 2026.7.4 / trl 0.24.0 / torch 2.10 / peft 0.19.1, across Qwen2.5-0.5B and Gemma-2-2B.

<Warning>
Older Unsloth releases (`< 2025.9.1`) and the pre-0.9 TRL API are no longer supported. If you had pinned `trl<0.9.0`, upgrade to `trl>=0.18.2`. The conda setup script now targets Python 3.11 + CUDA 12.4 + torch 2.6.0.
</Warning>

**Required for training:**
1. Huggingface token
2. Base model to train on (e.g. unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit)
3. Dataset to train on (e.g. yahma/alpaca-cleaned)
4. Huggingface model name to upload to (e.g. mervinpraison/llama3.1-instruct) (Optional)
5. Ollama model name to upload to (e.g. mervinpraison/llama3.1-instruct) (Optional)

If training dependencies are missing when you run `praisonai-train llm`, you'll see one of two messages depending on what's installed.

## Supported model families

The trainer uses each base model's own chat template by default — no more force-applied Llama template — so Gemma, Qwen, and Llama all format correctly out of the box.

| Model family | Example base model | `chat_template` value |
|--------------|--------------------|-----------------------|
| Llama 3.x | `unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit` | `"llama-3.1"` (or leave unset — model has its own) |
| Gemma 2 / Gemma 3 | `unsloth/gemma-2-2b-it-bnb-4bit` | `"gemma"` (or leave unset) |
| Qwen 2.5 / Qwen 3 | `unsloth/Qwen2.5-0.5B-Instruct-bnb-4bit` | `"qwen-2.5"` (or leave unset) |
| Mistral / Phi | via native template | leave unset |

<Warning>
If your base model has no built-in chat template, set `chat_template` in `config.yaml` — otherwise the trainer raises a `ValueError` at model-prep time:

```
ValueError: Tokenizer for model '<name>' has no chat template and none was
```

## To upload to ollama.com (Linux)

```bash
sudo cat /usr/share/ollama/.ollama/id_ed25519.pub
```

Save the output to ollama.com → Ollama keys.

<Note>
You no longer need to run `ollama serve` manually. The trainer starts the Ollama daemon automatically if it isn't already running, then creates and pushes the model. Requires the `ollama` CLI on PATH — install from [ollama.com](https://ollama.com).
</Note>

<Note>
**Supported Ollama templates:** Llama, Qwen, Mistral, Phi, DeepSeek, LLaVA, and Gemma. Any other model falls back to a Llama-style template. Gemma folds the system prompt into the first user turn (per the Gemma chat template spec) and stops on `<end_of_turn>` / `<start_of_turn>`.
</Note>

<Note>
PraisonAI Train is tested on Linux with pytorch-cuda 12.4 and Python 3.11 (2× RTX A6000). The `[llm]` extra pulls the modern Unsloth stack — minimum floors: `torch>=2.6.0`, `transformers>=4.51.3`, `unsloth>=2025.9.1`, `trl>=0.18.2`, `peft>=0.13.0`, `accelerate>=0.34.0`, `bitsandbytes>=0.45.0`. </Note>

### Ollama template selection

The trainer picks an Ollama `TEMPLATE` and stop-token block per model family, matched case-insensitively against `model_name`.

| Family keyword | Turn markers / templating | Stop tokens |
|---|---|---|
| `llama` | `<|start_header_id|>` / `<|eot_id|>` header blocks | `<|start_header_id|>`, `<|end_header_id|>`, `<|eot_id|>` |
| `qwen` | `<|im_start|>` / `<|im_end|>` (adds `num_ctx 32768` + Qwen system prompt) | `<|endoftext|>` |
| `mistral` | `[INST] ... [/INST]` | `[INST]`, `[/INST]` |
| `phi` | `<|im_start|>...<|im_sep|>` | `<|im_start|>`, `<|im_end|>`, `<|im_sep|>` |
| `deepseek` | bare role content | — |
| `llava` | `<|im_start|>` / `<|im_end|>` | `</s>`, `USER:`, `ASSSISTANT:` |
| `gemma` | `<start_of_turn>` / `<end_of_turn>`, system folded into first user turn | `<end_of_turn>`, `<start_of_turn>` |
| anything else | falls back to a Llama-style header template | `<|start_header_id|>`, `<|end_header_id|>`, `<|eot_id|>` |

See the full templates in the trainer source (`prepare_modelfile_content`).

<Note>
Ollama exports now use the correct template for Gemma models. Previously Gemma exports inherited the Llama template and produced garbled responses.
</Note>

<Warning>
When the base `model_name` matches no known family (`llama`, `qwen`, `gemma`, `mistral`, `phi`, `deepseek`, `llava`), the trainer prints `WARNING: no known chat template matched model '<name>'; using a generic template — stop tokens may be wrong.` and falls back to a generic Llama-style template. Set `model_name` to a recognized family to get the right stop tokens. The DeepSeek stop-token block is now the single `<｜end▁of▁sentence｜>` marker (previously four empty strings that emitted broken `PARAMETER stop` lines).
</Warning>

### Ollama environment variables

Point the trainer at a configured or remote daemon and a bigger models disk.

| Variable | Purpose | Default | When to set |
|----------|---------|---------|-------------|
| `OLLAMA_HOST` | Address the trainer probes and where `ollama create`/`push` publish to. Accepts `host`, `host:port`, or `http://host:port` (IPv6 literal `[::1]:11434` supported). | `127.0.0.1:11434` | A configured or remote Ollama daemon on a non-default host — stops the trainer ignoring a healthy remote daemon. |
| `OLLAMA_MODELS` | Directory Ollama stores models in. The trainer pre-checks free space on this volume before `ollama create`. | `~/.ollama/models` | The default volume is small — point at a large disk with `export OLLAMA_MODELS=/big/disk/ollama-models`. |

### Disk pre-check

Before `ollama create` runs, the trainer estimates the space it needs at **~1.5× the source model size** and refuses to start if the `OLLAMA_MODELS` volume has less free:

```
Not enough disk for the Ollama model: 4.2 GB free on '/home/me/.ollama/models', need ~15.0 GB. Point Ollama at a bigger disk, e.g. `export OLLAMA_MODELS=/big/disk/ollama-models`.
```

<Note>
The check is skipped when the source model size can't be measured locally (e.g. the Modelfile's `FROM` points at a Hub id rather than a file on disk) — so small Hub-backed exports on modest volumes aren't blocked with a false positive.
</Note>

### Quantization passthrough

`quantization_method` in the config flows through to `ollama create --quantize <q>`, so models aren't stored as huge `f16`. It's the same key GGUF export uses, and it's validated against the [12 valid values](#preflight-validation) up front.

### Daemon startup + surfaced errors

If the trainer starts `ollama serve` and the HTTP API on `/api/version` doesn't respond within **15 seconds**, the raised `RuntimeError` includes the `ollama serve` stderr — so `port in use` or a bad `OLLAMA_HOST` shows up in the error instead of vanishing.

### Push failures & key registration

A push whose stderr matches `unauthorized` / `401` / `403` / `forbidden` / `invalid key` translates to a key-registration hint, with your public key inlined when it's readable so you can paste it straight into ollama.com:

```
Ollama rejected the push (unauthorized). Register your public key at https://ollama.com/settings/keys and make sure the model is namespaced as `<username>/<name>`.

Your public key (~/.ollama/id_ed25519.pub):
ssh-ed25519 AAAAC3Nz...
```

A non-zero exit from `ollama create` raises a `RuntimeError` with the captured stderr (e.g. `` `ollama create me/model:latest` failed: Error: invalid Modelfile ``) instead of a raw `CalledProcessError` traceback.

### Silent-behaviour notes

The trainer prints these at runtime — they change results without erroring, so know them up front.

<Note>
**`num_samples` takes the FIRST N rows *before* shuffle.** Without `shuffle: true` you always train on the head of the dataset (often sorted by source/topic and unrepresentative). Add `shuffle: true` to sample randomly.
</Note>

<Warning>
**A validation split is concatenated into training, not held out.** A `split_type` of `validation`, `valid`, `test`, or `eval` is added to the training data. Use `val_split_ratio` for a true held-out eval set.
</Warning>

<Note>
**No length set means 2800 steps.** With neither `num_train_epochs` nor `max_steps` set, the trainer silently defaults to `max_steps: 2800`. Set `num_train_epochs: 1-3` (or `max_steps`) explicitly to control training length. When both are set, `max_steps` wins.
</Note>

## Multi-GPU

Launch across every GPU with one `torchrun` command — the trainer detects the distributed launch and handles DDP.

```bash
torchrun --nproc_per_node=2 -m praisonai_train.train.llm.trainer train --config config.yaml
```

```mermaid
graph LR
    Launch[🚀 torchrun] --> R0[⚙️ rank 0]
    Launch --> RN[⚙️ rank N]
    R0 --> Load0[🧠 per-rank model load]
    RN --> LoadN[🧠 per-rank model load]
    Load0 --> Save[✅ rank-0 save + publish]
    LoadN --> Save

    classDef input fill:#8B0000,stroke:#7C90A0,color:#fff
    classDef gpu fill:#189AB4,stroke:#7C90A0,color:#fff
    classDef process fill:#6366F1,stroke:#7C90A0,color:#fff
    classDef output fill:#10B981,stroke:#7C90A0,color:#fff
```

Each rank loads the full model on its own GPU (`device_map = {"": local_rank}`), Unsloth runs through its DDP-safe checkpointing path, and only rank 0 writes the final adapter and publishes. Set `ddp_find_unused_parameters: false` for a small speedup on dense-text models (leave the default `true` for multimodal / MoE). See [Multi-GPU](/docs/features/praisonai-train-multigpu) for the full walkthrough.

## Checkpointing & Resume

Save mid-run so an interruption never costs the whole training — then resume from the latest.

| Key | Type | Default | Description |
|---|---|---|---|
| `save_strategy` | `"no" \| "steps" \| "epoch"` | `"steps"` if `save_steps` set, else `"no"` | When to write checkpoints. |
| `save_steps` | `int` | `100` | Step interval when `save_strategy: steps`. |
| `save_total_limit` | `int` | *unset* | Keep only the N most recent checkpoints. |
| `resume_from_checkpoint` | `bool \| str` | `false` | `true` = latest in `output_dir`; a path = that checkpoint. |
| `final_model_dir` | `str` | `"lora_model"` | Where the final adapter is saved. |

Resume after an interruption — re-launch the same command with:

```yaml
resume_from_checkpoint: true   # picks the latest checkpoint in output_dir
```

See [Checkpointing](/docs/features/praisonai-train-checkpointing) for the full reference.

### Preflight checks

| Publish target set | `ollama_save: true` but `ollama_model` missing | `ollama_model is required when ollama_save is enabled.` |
| CUDA available (only when `train: true`, default) | No CUDA GPU | `No CUDA GPU detected. Fine-tuning needs a GPU. On a rented box check the driver; on CPU it cannot run.` |

```
  model_name: unsloth/gemma-2-2b-it-bnb-4bit
  max_seq_length: 2048
  dataset:
    - name: yahma/alpaca-cleaned
```

### GPU check

Enforced only when `train: true` (the default). A publish-only or export-only run (`train: false`) is valid on CPU — cross-link [Publishing](#publishing).

```
No CUDA GPU detected. Fine-tuning needs a GPU. On a rented box check the driver; on CPU it cannot run.
```

### Hugging Face credentials

When publishing is enabled, **either** an `HF_TOKEN` / `HUGGING_FACE_HUB_TOKEN` env var **or** a cached `huggingface-cli login` (read via `huggingface_hub.get_token()`) is accepted — you don't need both.

```
Publishing to Hugging Face is enabled but no credentials were found. Run `huggingface-cli login` or `export HF_TOKEN=hf_...`. To train without publishing, set huggingface_save: false.
```

<Tip>
Already ran `huggingface-cli login`? You do **not** also need to `export HF_TOKEN` — the cached login counts.
</Tip>

### Disk headroom

The trainer needs at least **10 GB** free on the `output_dir` volume (or `.` when `output_dir` is unset).

```
Low disk: only 3.2 GB free on the training disk (need ~10 GB minimum). Free up space or set output_dir to a larger disk.
```

### Quantization method

Enforced only when a GGUF or Ollama push is enabled. Valid values: `q4_k_m`, `q5_k_m`, `q8_0`, `q4_0`, `q4_1`, `q5_0`, `q5_1`, `q3_k_m`, `q6_k`, `f16`, `bf16`, `q2_k`. An unknown value lists all valid choices.

### Unknown keys

Unrecognized keys don't crash — the trainer collects **all** of them and prints one block with the closest known key suggested via `difflib`:

```
WARNING: unrecognized config key(s) — these will be ignored:
  - num_sample  (did you mean 'num_samples'?)
  - max_step    (did you mean 'max_steps'?)
```

Training continues after the warning.

<Warning>
**Clean errors, no tracebacks.** Preflight and known runtime failures print a single `ERROR: <msg>` line and exit with code `1`. Real bugs still show the full traceback. `Ctrl-C` exits with code `130` and a single `Interrupted.` line.

`dataset[].num_samples` must be a positive integer — `0`, negatives, and booleans raise `dataset[].num_samples must be a positive integer, got <value>`.
</Warning>

See [Export a trained model](/docs/features/praisonai-train-export) to publish an already-trained model without re-running training.

## Publishing

Publishing to Hugging Face or Ollama is opt-in — set the flag **and** the matching target.

```mermaid
graph TB
    Q1{Where to?}
    Q1 -->|Just training locally| Local[No flags<br/>saves to lora_model/]
    Q1 -->|Publish to HF| HF[huggingface_save: true<br/>+ hf_model_name]
    Q1 -->|Publish to Ollama| Ol[ollama_save: true<br/>+ ollama_model]

    classDef question fill:#F59E0B,stroke:#7C90A0,color:#fff
    classDef success fill:#10B981,stroke:#7C90A0,color:#fff
    classDef config fill:#6366F1,stroke:#7C90A0,color:#fff

    class Q1 question
    class Local success
    class HF,Ol config
```

`train: false` is a valid config — the trainer skips training **and** publishing (previously it crashed with an `AttributeError` on a `None` model).

### Publish without re-training

Already trained a model? Publish it with [`praisonai train export`](/docs/cli/train#praisonai-train-export) — no dataset, no re-training.

```bash
praisonai-train export hf     --model-dir lora_model --hf     me/my-model
praisonai-train export gguf   --model-dir lora_model --hf     me/my-model --quant q4_k_m
praisonai-train export ollama --model-dir lora_model --ollama me/my-model --quant q4_k_m
```

`for_export()` skips the training-only validation — an export-only run needs no `dataset:` (or a config file at all). See [Export an already-trained model](/docs/features/praisonai-train-package#exporting-an-already-trained-model).

### Publishing failure modes

Actionable messages replace raw HTTP tracebacks.

### Ollama publish knobs

Ollama exports quantize on create and can be redirected to a bigger disk.

- **`--quantize`** — `export ollama --quant q4_k_m` passes `--quantize` to `ollama create` so the model isn't stored as a huge `f16`.
- **`OLLAMA_MODELS`** — set this env var to point Ollama at a larger disk when short on space. The trainer disk-pre-checks it before `ollama create` and fails with `export OLLAMA_MODELS=/big/disk/ollama-models` guidance instead of a cryptic "no space left on device".
- **Push `401` / `403`** → an actionable message: register your public key (`~/.ollama/id_ed25519.pub`) at [ollama.com/settings/keys](https://ollama.com/settings/keys) and namespace the model as `<username>/<name>`. The key value is printed for you to copy.

### Hugging Face push errors

A rejected Hub push turns into a one-line fix, not a stack trace.

| Situation | Message you'll see | Fix |
|---|---|---|
| HF token invalid / expired | `Hugging Face rejected the token (401). It is invalid or expired — run \`huggingface-cli login\` or \`export HF_TOKEN=hf_...\` with a valid write token.` | New write-scoped token |
| HF wrong repo owner or read-only token | `No write access to '<repo>' (403). The repo must be under your own username and the token must have write scope. Set hf_model_name to '<your-username>/<name>'.` | Namespace to your user; write token |
| Ollama key not registered | `Ollama rejected the push (unauthorized). Register your public key at https://ollama.com/settings/keys and make sure the model is namespaced as '<username>/<name>'.` **plus** your key printed inline from `~/.ollama/id_ed25519.pub` | Paste the printed key at the URL |
| Ollama disk full | `Not enough disk for the Ollama model: X GB free on '<path>', need ~Y GB. Point Ollama at a bigger disk, e.g. \`export OLLAMA_MODELS=/big/disk/ollama-models\`.` | Move `$OLLAMA_MODELS` |
| Ollama daemon didn't start | `ollama serve did not become ready in 15 seconds. ollama serve output: <stderr>` | Fix the underlying stderr (port busy, bad `OLLAMA_HOST`) |
| `ollama create` failed | Raised as a `RuntimeError` with the create-command stderr, not a raw `CalledProcessError` | Follow the printed guidance |

<Note>
**Namespaced repo IDs are never deleted as local paths.** Setting `hf_model_name: "user/model"` (a Hub repo id) is never treated as a local dir to remove. The trainer only cleans up a stale local dir when the value has no `/` **and** actually exists on disk.
</Note>

<Note>
**Chat-template fallback warns loudly.** When no known family (`llama`, `qwen`, `gemma`, `mistral`, `phi`, `deepseek`) matches your `model_name`, the trainer prints `WARNING: no known chat template matched...` and falls back to a generic Llama-style template. Verify the Ollama output, or set `model_name` to a recognized family. Empty stop tokens are skipped, so the Modelfile never emits a broken `PARAMETER stop` line.
</Note>

<Warning>
Publish-auth failures translate to one clean, actionable line:

- **HF 401** — `Hugging Face rejected the token (401). It is invalid or expired — run huggingface-cli login or export HF_TOKEN=hf_... with a valid write token.`
- **HF 403** — `No write access to '<repo>' (403). The repo must be under your own username and the token must have write scope. Set hf_model_name to '<your-username>/<name>'.`
- **Ollama 401/403** — `Ollama rejected the push (unauthorized). Register your public key at https://ollama.com/settings/keys ...` and prints your local `~/.ollama/id_ed25519.pub`. The model must be namespaced as `<username>/<name>`.
</Warning>

</Note>

Everything else — a genuine bug — still shows its full traceback so it's not silently swallowed. `Ctrl-C` exits `130`.

## Silent-behaviour NOTES

Three behaviours that used to surprise users now print an explicit `NOTE:` / `WARNING:` line.

- **`num_samples` takes the first N rows before shuffle** — repeated runs with the same seed use the same deterministic subset.
- **`split_type` of `validation` / `valid` / `test` / `eval` is ADDED to the training set** — no validation set is held out. Warned via `WARNING: dataset split_type '<x>' is ADDED to the training set`.
- **Default `max_steps: 2800`** fires when neither `num_train_epochs` nor `max_steps` is set: `NOTE: neither num_train_epochs nor max_steps set; defaulting to max_steps: 2800. Set num_train_epochs: 1-3 (or max_steps) to be explicit.` When **both** are set, `max_steps` silently wins (logged at DEBUG).

## Advanced

Fine-tune loss to assistant turns only, in a model-agnostic way.

### Model & template keys

Two optional keys control how conversations are formatted and which tokens count toward the loss.

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `chat_template` | `str` | `None` | Unsloth chat-template name (e.g. `"llama-3.1"`, `"gemma"`, `"gemma-2"`, `"qwen-2.5"`, `"qwen-3"`, `"mistral"`, `"phi-3"`, `"chatml"`). Omit to keep the model's own built-in template. See Unsloth's `get_chat_template` for the full list. |
| `assistant_only_loss` | `bool` | `false` | Compute loss only on assistant turns (model-agnostic response-only loss). Requires a chat template exposing `{% generation %}` blocks. |

<Note>
Omit `chat_template` unless you're intentionally overriding — the model's own template is almost always what you want.
</Note>

### Model-agnostic response-only training

Leave `assistant_only_loss: auto` to let the trainer mask the loss to assistant turns whenever the template supports it — falling back to full-sequence SFT otherwise. Force it with `true` only when you know your template emits `{% generation %}` blocks.

```yaml
model_name: "unsloth/Meta-Llama-3.1-8B-Instruct-bnb-4bit"
chat_template: "llama-3.1"
assistant_only_loss: true   # force on — errors fast if the template can't mask
```

This uses TRL's model-agnostic `SFTConfig(assistant_only_loss=True)` instead of the old Llama-only `train_on_responses_only` markers. If you set `assistant_only_loss: true`, also set a `chat_template` that supports assistant masks (e.g. Unsloth's `llama-3.1`, `gemma-2`, `qwen-2.5`).

<Warning>
`assistant_only_loss: true` on a template without `{% generation %}` markers raises `ValueError` at model-prep time. Use `auto` (recommended) or `false`, or set a `chat_template` that supports masking (e.g. an Unsloth "llama-3.1-lite" style template extended with generation blocks).
</Warning>

<Warning>
If your tokenizer has no built-in chat template and you don't set `chat_template`, `praisonai-train llm` now raises `ValueError` at model prep time:

```text
Tokenizer for model '<model_name>' has no chat template and none was
provided via config 'chat_template'. Set 'chat_template' (e.g.
'gemma', 'qwen-2.5', 'llama-3.1') so conversations format correctly.
```

This replaces the earlier silent-empty-training bug — set `chat_template` (e.g. `gemma`, `qwen-2.5`, `llama-3.1`) to fix.
</Warning>

## Best Practices

<AccordionGroup>
<Accordion title="Start with praisonai-train alone if you only want agent training">
`pip install praisonai-train` pulls `praisonaiagents` plus `litellm` (for LLM-as-Judge grading) — enough for `agents`, `list`, `show`, and `apply`. Add `[llm]` only when you need Unsloth fine-tuning.
</Accordion>

<Accordion title="Set HF_TOKEN in the environment">
Export `HF_TOKEN` in your shell before fine-tuning so the trainer can push to Hugging Face. Never commit the raw token.
</Accordion>

<Accordion title="Start small, then scale">
Use a low `max_steps` and `num_samples: 20` for a first run — a full smoke test finishes in under a minute. Ramp up once the pipeline is green.
</Accordion>

<Accordion title="Leave assistant_only_loss: auto">
The trainer enables masking whenever the tokenizer supports it and falls back cleanly otherwise. Only set `true` / `false` if you need to force a specific behaviour.
</Accordion>

<Accordion title="Publish flags are opt-in">
For local experiments, delete the `huggingface_save` / `ollama_save` keys entirely — no target, no push, no crash. Set the flag **and** its target (`hf_model_name` / `ollama_model`) only when you want to publish.
</Accordion>

<Accordion title="Publishing needs credentials + write access — check them once">
Run `huggingface-cli login` (or `export HF_TOKEN=hf_...`) and namespace the repo under your own username. [Preflight](#preflight-validation) catches missing credentials before the run; a rejected push still [translates 401/403](#publishing-failure-messages) into an actionable fix. For Ollama, register your signing key at ollama.com — a rejected push [prints your public key to copy](#push-failures--key-registration).
</Accordion>

<Accordion title="Track runs with Weights & Biases">
Set `PRAISON_WANDB=True` and the `WANDB_*` variables to log loss curves and checkpoints for each run.
</Accordion>

<Accordion title="Let the tokenizer's native template win">
Only set `chat_template` for models without one, or to force a specific one. Forcing `llama-3.1` on Gemma/Qwen was the old default and silently corrupted training — now the trainer uses each model's own template by default.
</Accordion>

<Accordion title="Match chat_template to your model family">
Omit `chat_template` to use the model's built-in template — that's correct for most Instruct models. Set it explicitly (`gemma`, `qwen-2.5`, `llama-3.1`, ...) only when overriding or when the tokenizer ships no template, otherwise the trainer raises `ValueError` at model prep.
</Accordion>

<Accordion title="Enable assistant_only_loss for instruction datasets">
Turn on `assistant_only_loss: true` so loss is computed only on assistant turns — but confirm your chat template exposes `{% generation %}` blocks (e.g. Unsloth's `llama-3.1`, `gemma-2`, `qwen-2.5`). Templates without them cannot produce the mask and TRL will error.
</Accordion>
</AccordionGroup>
